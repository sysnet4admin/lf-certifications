# MCP 2026-07-28 스펙에서 바뀐 것

> 개인적으로 정리한 자료이며 리눅스 재단(Linux Foundation)과 AAIF의 공식 자료가 아니다. 공식 스펙이 우선이다: https://modelcontextprotocol.io/specification/2026-07-28

MCPA 공식 페이지가 준비 기준으로 지정한 스펙 버전이다. 이전 버전은 2025-11이다. 릴리스
후보는 2026-05-21에 고정됐고 정식 스펙은 2026-07-28에 나왔다. 2026-09-30에 공식 블로그를
보고 정리했다.

이전 자료로 공부하면 없어진 것을 외우게 된다. 2025년 자료의 세션과 handshake 설명이 특히 그렇다.

## 한눈에 보기: 이전 방식과 새 방식

2026-07-28 변경은 대부분 "server가 연결별 상태를 기억하지 않는다"는 원리 하나로 설명된다. 예전에
server가 기억하던 것을 이제는 요청에 직접 넣는다. 왼쪽 열의 방식은 2026-07-28 기준으로
틀린 설명이다.

| 이전 방식 | 2026-07-28 |
|---|---|
| `initialize`로 처음에 인사하고 버전과 capability를 기억한다 | 요청마다 `_meta`에 버전과 capability를 넣는다 |
| `Mcp-Session-Id`로 세션을 유지한다 | 세션이 없다 |
| `resources/subscribe`로 URI마다 구독한다 | `subscriptions/listen` 스트림을 열고 구독할 URI 목록을 넣는다 |
| server가 열린 연결로 client에게 요청(sampling, elicitation)을 먼저 보낸다 | MRTR: server가 `input_required`를 돌려주고 client가 답을 채워 새 id로 다시 요청한다 |
| 끊긴 스트림을 `Last-Event-ID`로 이어 받는다 | 이어 받기가 없다. 새 id로 다시 요청한다 |
| roots, sampling, logging이 정식 기능이다 | 폐기 예정이다. 지금도 동작하고 2027-07-28 이후에 없어질 수 있다 |
| Dynamic Client Registration을 권한다 | 폐기 예정이다. Client ID Metadata Documents를 쓴다 |

바뀌지 않았지만 잘못 알기 쉬운 규칙도 함께 적는다.

- tool annotation은 보장이 아니라 힌트다. 신뢰하는 server가 보낸 값이 아니면 믿지 않는다.
- server는 사용자의 token을 상위 API로 그대로 넘기면 안 된다. 자기에게 발급된 token만 받는다.
- `clientInfo`는 client가 스스로 적는 값이다. 화면 표시와 로그에만 사용하고 권한 판단에 사용하지 않는다.

출처는 rohitg00 brief 1절과 16절(`others-exam/rohitg00/brief.ko.md`)이다.

## 프로토콜 구조: 상태 없는 방식으로

- `initialize`/`initialized` handshake를 없앴다.
- `Mcp-Session-Id` 헤더를 없앴다. HTTP GET 스트림도 없앴다.
- 요청마다 자기 정보를 포함한다. 프로토콜 버전, 클라이언트 정보, capability가 요청의 `_meta`에 들어간다.
- `server/discover` RPC를 추가했다. capability를 미리 알아보는 용도이고 사용하지 않아도 동작한다.

## 라우팅 헤더

- `Mcp-Method`: 메서드 이름으로 라우팅한다.
- `Mcp-Name`: 도구나 리소스 이름으로 라우팅한다.

## Multi Round-Trip Requests (MRTR)

전에는 서버가 스트림을 열어 둔 채 `elicitation/create`, `sampling/createMessage`, `roots/list`를
클라이언트에 먼저 보냈다. 이제는 서버가 응답으로 `resultType: "input_required"`를 돌려준다.
클라이언트는 `inputResponses` 필드에 답을 넣어 다시 요청한다.

## 캐시

목록 응답에 `ttlMs`와 `cacheScope` 필드가 생겼다. 대상은 `tools/list`, `prompts/list`,
`resources/list`, `resources/read`다.

## 확장(Extensions) 체계

공식 확장 구조가 생겼다. 지금 있는 확장은 Tasks, MCP Apps, Enterprise Managed Authorization(EMA)이다.

Tasks는 실험 기능에서 `io.modelcontextprotocol/tasks` 확장으로 옮겼다. `tasks/get`으로 상태를
조회하고 `tasks/update`로 바꾼다. 알림은 `subscriptions/listen` 스트림으로 받는다.

## 인가(Authorization)

- 인가 응답의 `iss` 파라미터를 검증해야 한다(RFC 9207).
- Dynamic Client Registration에 `application_type`을 넣는다.
- client credentials에 issuer를 묶는다.
- Dynamic Client Registration은 폐기 예정이다. 대신 Client ID Metadata Documents(CIMD)를 쓴다.

## 폐기 예정

Roots, Sampling, Logging, 이전 HTTP+SSE transport가 폐기 예정이 됐다. 폐기 정책도 새로 생겼다.
폐기 예정이 된 기능은 최소 12개월 동안 남는다. 그래서 2026-07-28에 폐기 예정이 된 것은
2027-07-28 이후 버전에서만 없어질 수 있다. 스펙 변경은 SEP(Specification Enhancement
Proposal) 절차를 거친다.

## SDK

TypeScript, Python, Go, C# SDK가 이 버전을 지원한다. Rust SDK는 베타다.

SDK 등급은 스펙 릴리스 뒤에도 바뀐다. 공식 SDK 페이지(`docs/docs/2026-07-28/sdk.mdx`) 이력으로 확인했다(2026-10-14).

| 시점 | Tier 1 | Tier 2 | Tier 3 |
|---|---|---|---|
| 2026-07-28 릴리스 | TypeScript, Python, C#, Go | Java, Rust | Swift, Ruby, PHP, Kotlin |
| 2026-10-14 | TypeScript, Python, C#, Go, Rust, Ruby | Java | Swift, PHP, Kotlin |

Rust는 2026-08-21에, Ruby는 2026-09-28에 Tier 1이 됐다. 이 저장소의 문제는 릴리스 시점 목록을 기준으로 답한다.

## 보안 도메인 요점 (WorkOS 글에서, 2026-10-13 추가)

[WorkOS 글](https://workos.com/blog/mcpa-certification-security-and-governance)이 짚은 함정이다. 스펙 원문
인가(Authorization) 절과 같이 본다.

- 토큰이 유효한지보다 이 서버를 위해 발급됐는지(audience)가 중요하다. 받은 토큰을 상위 API로 그대로
  넘기지 않는다. 필요하면 새 자격 증명으로 교환한다.
- 동의는 연결할 때 받는다. 인가 확인은 도구를 호출할 때 한다.
- scope를 다시 요청하는 것(scope step-up)과 본인 확인을 다시 하는 것(authentication step-up)은 다르다.
- 도구 annotation은 힌트일 뿐 보안 통제가 아니다.
- stdio transport는 OAuth를 사용하지 않고 환경 변수에서 자격 증명을 읽는다. 인가 요구 사항은 transport에 따라 다르다.
- 세션이 없어졌으므로 감사 로그에 어느 에이전트가 누구의 권한으로 했는지를 남겨야 한다.
- 전제 지식: OAuth 2.1과 PKCE, protected resource metadata, resource indicator(audience 지정).
